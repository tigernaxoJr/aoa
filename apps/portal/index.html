Architecture pattern

Run your product's agent
on the user's side

AOA offloads a product's agent work — LLM reasoning, tool use, and the tokens they consume — to the coding agent the user already has (Claude Code, Codex, Cursor, Gemini CLI, Pi…). The service keeps whatever else it needs, including a backend or lightweight models.

02 / Architecture

Brain & engine

Who runs the agent's inference, and who pays for its tokens.

The agent part of a product needs a brain (LLM inference) and an engine (the tokens that inference consumes). In cloud SaaS the vendor supplies both and bills them back as subscriptions. AOA hands both to the agent the user already has; the service provides the interface and the specification, and keeps the rest of its stack.

Service

Interface & spec

  • A web workbench, an API, or both
  • Specifications at URLs: guide, schemas, skill
  • Validates what the agent returns

Doesn't run or pay for the agent

Brain

LLM inference

  • Understands the request, plans the steps
  • Writes files, calls local tools (FFmpeg, Playwright, TTS)
  • Runs in the user's agent: Claude Code, Codex, Cursor, Pi…

The model the user chose

Engine

Tokens

  • Supplied by the user
  • Their agent plan's quota, or local hardware
  • Near-zero marginal cost for the service

The user's plan · or local

There is no private channel between the two: the agent reads the specification from a URL and returns results through files or the API. The frontend tools here treat a folder the user grants as the single source of truth.

03 / Principles

Four principles

What makes an architecture AOA.

  1. 01

    Offloaded agent work

    Work that needs an agent's reasoning and tools runs in the user's agent, on the user's tokens. The service may still run a backend, databases, or lightweight models.

  2. 02

    Schema as the contract

    The service and the agent coordinate through published JSON Schemas, not private APIs; everything the agent writes is validated.

  3. 03

    Files or API as the bus

    Frontends use a local folder as the single source of truth and detect changes by file-metadata fingerprints; backend-only services expose the same contract over an API.

  4. 04

    Local-first, user-chosen boundary

    Files the agent works on stay with the user. The only third party that sees that context is the LLM provider the user chose — none, with a local model.

Move inference at your own pace · cloud to on-prem, same product

Where inference runs is a setting in the user's agent; the service only knows the protocol. Teams can start on a mainstream cloud plan (Anthropic, OpenAI, or a CSP-hosted service such as AWS Bedrock, Google Vertex AI, or Azure OpenAI) to prove the workflow quickly, then point the same agent at a self-hosted model served with Ollama or vLLM once the data gets more sensitive, so nothing leaves the network. The service, the frontend, and the project format don't change along the way.

04 / Comparison

Cloud SaaS vs. AOA

AOA doesn't make inference free. It moves the agent's inference to a plan the user already pays for, or to their own hardware.

Cloud GenAI SaaS AOA
Hosting GPU servers, databases, bandwidth Static files on a CDN, or a backend without the agent's load
Agent inference Paid by the vendor, recovered through subscriptions The user's existing agent plan, or a local model
User files Uploaded to and stored in the vendor's cloud Stay on the user's machine
Output A black box; regenerate if unhappy Plain files (MD, SVG, Vue, PDF) editable at any step
Operations 24/7 backend monitoring Only what the service itself keeps; none for a static site

05 / Modes

Three collaboration modes

From a zero-setup frontend to a pure API with no frontend at all. Adopt them progressively.

A
Pure workbenche.g. all three tools here
A static page reads and writes a folder the user grants, polls it for changes, and hands the user commands to paste into their agent. Nothing to install.
B
Frontend + backendTeams, billing, live collaboration
A cloud control plane handles accounts, billing, and team sync. The agent operates the backend through an API or MCP server, and the backend pushes each change to the page over WebSocket, SSE, or gRPC, so the user watches the UI update step by step and can take over at any point. Inference, tokens, and private data stay on the user's side (bring your own agent).
C
Backend onlyThe agent operates an API
No web UI. The service exposes an API; the agent reads its specification and calls it directly. The service keeps data and state but doesn't run the agent. It can also ship as an MCP server.

Why Mode B · the agent drives, the UI shows it live

  • Live updates, no polling: every API call the agent makes becomes an event the backend pushes, and the page redraws at once.
  • See what the agent is doing: progress, intermediate results, and errors appear in the UI, not only in a terminal.
  • One shared state for user and agent: edits made in the page go back to the backend and become the agent's next input, so the two can hand work back and forth.
  • The page can assign work: while the agent stays connected, the page can queue tasks on the backend for the agent to pick up, with no command to copy and paste.
  • Teams stay in sync: everyone on a project sees the agent's changes at the same time.
  • The backend stays thin: it validates, stores state, and broadcasts events; inference and tokens remain with the user's agent.

In every mode · a specification entry point

The agent first needs the specification, and the entry point is usually a URL: a guide page, an OpenAPI document, or an index. This platform publishes a central index at /api/index.json, with dedicated endpoints for Story Video Studio, Product Video Studio and Slide Studio.

06 / Limitations

Limitations & trade-offs

What to evaluate before adopting AOA. The first two depend on the user's environment; the last two must be handled in product design.

  • Browser support (frontend modes)

    Folder access needs the File System Access API: desktop Chrome and Edge today. Brave disables it by default; Firefox and Safari don't support it.

  • Users bring their own agent

    Users need a working agent setup and pay for their agent plan or local model themselves.

  • Agents are non-deterministic

    Agent output must be validated against the schema, with retry and repair paths.

  • The page can't wake the agent (Mode A)

    The user starts the agent and pastes the command the page prepares; the page only reflects what the agent writes. In Mode B, a connected agent can pick up tasks the page queues on the backend.
